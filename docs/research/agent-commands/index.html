Field report · 2

The made-up package names are in the instructions, not the code

I scanned 991 public repos built with AI coding agents. Like last time, their code didn't import a single made-up package. But their READMEs and agent instruction files contain 50,301 install and run commands, and 560 of the package names in them aren't on npm. Coding agents read those files and run those commands.

Scanned 2026-11-14 Published 2026-11-14 Corpus 991 repositories · 649,213 source files Tool ghostimport v0.7.1, rescored with v0.7.2

Method

How I picked the repos

The first report looked at 174 repos. This time I wanted a bigger sample, and repos where I could be sure an AI agent was involved. So I used GitHub code search to find repos that contain an agent instruction file, which is the file a coding agent reads before it starts working.

A repo can have more than one marker.

Code search found 11,220 repos. I kept the JavaScript and TypeScript ones that weren't forks or archived, and took the top 1,000 by stars. 991 scanned cleanly. These are mostly small projects: the median has 13 stars, and only 31 have more than 1,000. That's what code search returns, not a sample of the most popular repos on GitHub.

For each repo I did two things:

  • Imports. Ran ghostimport --json on the code, like in the first report.
  • Commands. Pulled every npm, npx, pnpm, yarn and bun command out of code blocks in Markdown files, agent instruction files and package.json scripts. Then I worked out which packages each command would install or run, using the same parser as the ghostimport agent hook, and looked every name up on npm.

I only used public data: the GitHub API and the public npm registry. Nothing from these repos was executed, I didn't register any package names, and I'm not naming any repo.

Most of the 560 are harmless once you look at them. They are placeholders like your-cli-package-name, packages a monorepo README tells you to install before they've been published, and sentences that just happen to start with npm.

But a person reads your-cli-package-name and knows it's an example. An agent that has been told to follow the README might just run it. And some of the names look exactly like what a model would invent:

  • npm install -g opencode appears in 8 repos, all in a copied agent template. The real package is opencode-ai. This one can't be abused: a package called open-code already exists, and npm doesn't let anyone register a name that differs from an existing one only by punctuation.
  • A .cursorrules file in 2 repos tells the agent to install a package that has never existed. The functionality lives under a subpath of a different package. I'm not naming it, because when I checked, anyone could still register it.

ghostimport says up to 321 of the missing names could be registered by anyone, 18 of them in agent instruction files. That's an upper bound: ghostimport doesn't check npm's punctuation rule yet, and opencode shows that it matters. I'm not publishing the list.

Finding 03

Command names aren't package names, and someone has noticed

npx foo first looks for a command called foo in the project's installed packages. If there isn't one, for example in a fresh clone before npm install, it downloads and runs the npm package called foo. Many tools install a command whose name differs from the package name, so docs that say npx foo work on the author's machine and fetch something else everywhere else.

Command in docsThe tool it meansWhat npx fetches without itRepos
npx jsdoc2mdjsdoc-to-markdownA placeholder that prints a warning4
npx depcruisedependency-cruiserA placeholder that prints a warning3
npx cucumber-js@cucumber/cucumberA placeholder that prints a warning2
npx easeas-cliAn unrelated templating library from 2017, by another author3

The three placeholders were registered in July 2025 "to prevent dependency confusion". Their README points to Aikido Security's threat intelligence. I read their code and didn't run it: it only prints a warning. So someone is already registering these names before attackers do. That's good, but it only covers the names someone has spotted.

ghostimport rates all four as high risk. Since 0.7 its agent hook also checks npx, dlx and bunx runs, so it blocks these commands and tells the agent to find the real tool.

Finding 04

The scan found six bugs in ghostimport

Like in August, running the tool on real code found problems the tests didn't. The worst one would have made the agent hook block ordinary commands: it read npm install # Install dependencies as a request to install two packages, Install and dependencies.

BugWhat went wrong
Shell commentsWords after # were read as package names

All six are fixed in 0.7.2, each with a test.

Still not fixed

  • Import statements inside comments and strings are reported as imports.
  • something.require("x") is read as a require call.
  • Dependencies installed from GitHub, a tarball or under an alias (npm:, github:, file:) are looked up on npm and reported as missing.
  • The "free to register" check ignores npm's punctuation rule, so it overcounts.
  • Type-only imports of packages that exist only as @types/*, like estree, are reported as missing.
  • When npm's downloads API doesn't answer, which happens on big runs, old single-version packages fall to high risk. In the agent hook, that means a block the agent has to explain to you.

Check your own repo

You don't need my data. Scan your code, then look up the names in the install and npx commands in your README and agent files.

check it yourself
$ npx ghostimport@0.7.2 ./your-repo
$ npm view <name-from-a-command>   # a 404 means nobody has published it

If you write agent instructions, check the commands in them

An agent instruction file is a script someone else's agent will run. Every npx line in it should name the package that's on npm, not the command it installs, and every install line should name a package that exists. If you use Claude Code, the ghostimport hook checks each command before the agent runs it.
