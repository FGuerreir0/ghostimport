Field report

Hallucinated imports don't survive to a public repository

We scanned 174 public GitHub repositories looking for npm imports that resolve to nothing. The hallucinations we went looking for were not there. What the scan did turn up is below: a null result, one finding held back under coordinated disclosure, and six bugs in our own scanner.

Scanned 2026-08-30 Published 2026-09-13 Corpus 174 repositories · 23,773 source files · 4,555 unique imports Tool ghostimport v0.5.2

Method

Two cohorts, because one of them was the control

A hallucinated import is supposed to be an AI problem, so scanning only well-maintained projects would prove nothing either way. We built two groups: the most popular JavaScript and TypeScript repositories on GitHub, and a set of recent repositories whose READMEs advertise that they were built with an AI tool.

CohortSelectionReposFiles
Established Over 5,000 stars, JS or TS — axios, redux, date-fns, react-hook-form, socket.io 4710,894
AI-assisted Created after 2025-06, README says “vibe coded”, “built with Cursor”, or credits another AI coding tool 12712,879

Each repository was downloaded as a tarball from the GitHub API, scanned with ghostimport --json, and discarded. Every name reported as missing was then checked by hand against the live registry. That last step is the one that matters, and it is the reason this report claims less than we expected it to.

Everything used public data only: repository tarballs and code search through the GitHub API, and the public npm registry. We ran no code from any repository, registered no package names, and contacted no project except through its published disclosure channel.

Finding 01

Hallucinated imports do not survive to a public repository

0
Organic hallucinations
Across all 174 repositories, in both cohorts.
4,555
Unique imports checked
All but three resolved, were local, or were deliberate fixtures.

This is a null result, and it is worth stating plainly because it undercuts the pitch most tools in this space make, including the one we started with. A package name your AI invented breaks the build the first time anyone runs npm install. It gets noticed in seconds and fixed before the commit. By the time code reaches a public repository, the build has already filtered that mistake out.

The corollary is the useful part: scanning finished repositories is the wrong place to look. The window where a hallucinated name is dangerous is the minute between the agent writing it and the developer running the install — which is why ghostimport ships as an MCP server and an agent hook, not only as a linter.

One trap worth naming

Our first pass turned up a cluster of convincing hallucinations — @anthropic/sdk, @openai/api, @langchain/agents — exactly the names a language model would invent, none of which exist. They all came from a single repository: another open-source tool in this space, whose test suite deliberately contains fake package names. That is why every name in this report was opened and checked by hand.

Finding 02

Held back under coordinated disclosure

One result from this scan concerns a third-party product. We reported it privately on 2026-08-30 through the vendor's vulnerability disclosure program, and it has not been resolved yet. Until it is, or until the program's disclosure terms allow it, this report publishes nothing that describes it: not the product, not the affected files, not the scale.

This section will be updated when that changes. We have not registered any package name found in this scan, and will not.

Unpublished is not the same as squattable

Two other names the scan confirmed as unpublished were scoped packages, imported by example projects inside the repository that uses them. Neither is squattable: the scope already has an owner on npm, and only a scope's owner can publish under it.

That distinction is easy to miss. ghostimport v0.5.2 missed it too, and reported both names as free to register. From v0.6.0 it checks whether a scope is owned before calling a scoped name squattable.

Finding 03

What the corpus found in ghostimport itself

A scanner that reports a problem in one popular repository out of four is not a security tool, it is a nuisance. This corpus was the first time ghostimport had been pointed at a large body of real-world code, and it did not come out of it well.

Measurev0.5.1v0.5.2
Established repos reporting a missing package19.1%12.8%
AI-assisted repos reporting a missing package11.8%5.5%
Distinct false names reported5525

Six causes, all fixed in v0.5.2:

CauseWhat it broke
Root-only configA monorepo's nested package.json and tsconfig.json were invisible, so workspace packages looked missing
Scoped aliasesThe alias @commands was stored, then compared against the import @commands/types — it could never match
Comment strippingThe JSONC parser ate https:// inside strings, destroying every Deno import map it read
Framework scopes@theme/* and @site/* are resolved by Docusaurus, @std/* by Deno — none are npm names
Build output.vercel and friends were walked, so bundled vendor code was scanned as though someone had imported it
Non-JS specifiersshared.dart was parsed as a package name, because dots are legal in npm names

Two thirds of what remains is deliberate: fake names inside test fixtures, in projects that test import parsing. We chose not to suppress test directories. Agents write tests too, and a hallucinated import in a test file is still a real one.

Reproduce it

None of this needs our data. Point the scanner at any repository and check the names it reports against the registry yourself.

reproduce
$ npx ghostimport@0.5.2 ./some-repo --json
$ npm view <name-it-reported>   # a 404 means the name is free

If you ship templates, check the names they import

Any scaffold, starter template, internal CLI or documentation example that emits an import is publishing a claim on a package name. If that name is unregistered, anyone can answer the claim. Checking takes one command per name, and it is worth running against every template you ship.
