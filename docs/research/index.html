Field report

404 repositories import a package that nobody owns

We scanned 174 public GitHub repositories looking for npm imports that resolve to nothing. The hallucinations we went looking for were not there. What we found instead was a single name, emitted by an AI app builder into hundreds of repos, that has never been published — and is free for anyone to claim today.

Scanned 2026-08-30 Published 2026-09-13 Corpus 174 repositories · 23,773 source files · 4,555 unique imports Tool ghostimport v0.5.2

Method

Two cohorts, because one of them was the control

A hallucinated import is supposed to be an AI problem, so scanning only well-maintained projects would prove nothing either way. We built two groups: the most popular JavaScript and TypeScript repositories on GitHub, and a set of recent repositories whose READMEs advertise that they were built with an AI tool.

CohortSelectionReposFiles
Established Over 5,000 stars, JS or TS — axios, redux, date-fns, react-hook-form, socket.io 4710,894
AI-assisted Created after 2025-06, README says “vibe coded”, “built with Cursor”, or names another AI app builder 12712,879

Each repository was downloaded as a tarball from the GitHub API, scanned with ghostimport --json, and discarded. Every name reported as missing was then checked by hand against the live registry. That last step is the one that matters, and it is the reason this report claims less than we expected it to.

Finding 01

Hallucinated imports do not survive to a public repository

0
Organic hallucinations
Across all 174 repositories, in both cohorts.
4,555
Unique imports checked
Every one resolved, was local, or was a deliberate fixture.

This is a null result, and it is worth stating plainly because it undercuts the pitch most tools in this space make, including the one we started with. A package name your AI invented breaks the build the first time anyone runs npm install. It gets noticed in seconds and fixed before the commit. By the time code reaches a public repository, the build has already filtered that mistake out.

The corollary is the useful part: scanning finished repositories is the wrong place to look. The window where a hallucinated name is dangerous is the minute between the agent writing it and the developer running the install — which is why ghostimport ships as an MCP server and an agent hook, not only as a linter.

One trap worth naming

Our first pass turned up a cluster of convincing hallucinations — @anthropic/sdk, @openai/api, @langchain/agents — exactly the names a language model would invent, none of which exist. They all came from a single repository: a competing tool whose test suite deliberately contains fake package names. Anyone publishing a percentage without opening the files is counting someone else's fixtures.

Finding 02

One unregistered name, shipped by a code generator into hundreds of repos

The registry has never held this name. It is free to claim.

The name is imported by the same two configuration files in repository after repository. Those files are near-identical across projects that have nothing else in common, which is the signature of a scaffold: they are emitted by an AI app builder into the projects it generates.

The package does not exist on npm. It never has. The registry answers a request for it with a 404 — which is also, as it happens, the number of public repositories that import it.

Code search returns 657 file matches across 404 distinct public repositories. Every match is in one of those two files, in the layouts the scaffold emits. Private repositories are not indexed, so the real number is higher.

Why the name is withheld. We reported this privately to the vendor on 2026-08-30, through its vulnerability disclosure program, with a proposed publication date of 2026-09-13. As of that date we have had no response, and the name is still unregistered. Naming it now would hand anyone a ready-made list of targets, so this report leaves out the package, the vendor and the affected files. We will publish them once the name is reserved or the template is fixed.

Why this shape is the dangerous one

A hallucination in one developer's file is a build error. A name baked into a generator's template is a standing target: it is reproduced automatically, it looks official in a lockfile or a dependency review, and every project that has it waits on the same unclaimed name. Registering it would put attacker-controlled code one npm install away from every one of those repositories, with a postinstall script that runs before anybody reads a line of it.

We have not registered the name and will not. It has been reported so that the vendor can publish or reserve it before somebody else does.

The same pattern, smaller blast radius

The scan found this shape twice more. @the0/sdk and @the0/react are imported by the example projects inside their own repository, and neither has ever been published. Both names were unclaimed when this was written.

Finding 03

What the corpus found in ghostimport itself

A scanner that reports a problem in one popular repository out of four is not a security tool, it is a nuisance. This corpus was the first time ghostimport had been pointed at a large body of real-world code, and it did not come out of it well.

Measurev0.5.1v0.5.2
Established repos reporting a missing package19.1%12.8%
AI-assisted repos reporting a missing package11.8%5.5%
Distinct false names reported5525

Six causes, all fixed in v0.5.2:

CauseWhat it broke
Root-only configA monorepo's nested package.json and tsconfig.json were invisible, so workspace packages looked missing
Scoped aliasesThe alias @commands was stored, then compared against the import @commands/types — it could never match
Comment strippingThe JSONC parser ate https:// inside strings, destroying every Deno import map it read
Framework scopes@theme/* and @site/* are resolved by Docusaurus, @std/* by Deno — none are npm names
Build output.vercel and friends were walked, so bundled vendor code was scanned as though someone had imported it
Non-JS specifiersshared.dart was parsed as a package name, because dots are legal in npm names

Two thirds of what remains is deliberate: fake names inside test fixtures, in projects that test import parsing. We chose not to suppress test directories. Agents write tests too, and a hallucinated import in a test file is still a real one.

Reproduce it

None of this needs our data. Point the scanner at any repository and check the names it reports against the registry yourself.

reproduce
$ npx ghostimport@0.5.2 ./some-repo --json
$ npm view <name-it-reported>   # a 404 means the name is free

If you build a code generator, check your own templates

This finding took one command to confirm and would have taken one command to prevent. Any scaffold that emits an import is publishing a claim on a name; if that name is unregistered, the claim is an open invitation. This applies to starter templates, internal CLIs and documentation examples as much as to AI builders.
